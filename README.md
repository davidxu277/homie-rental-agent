## 1. 快速开始

```bash
npm install
cp .env.example .env.local     # 填入 ANTHROPIC_API_KEY（必需）
                               # 和 GOOGLE_MAPS_API_KEY（可选）
npm run dev                    # http://localhost:3000
```

其他命令：

```bash
npm test                # 213 个测试，全部纯函数 / 桩，不发网络请求
npm run clean           # 重跑数据清洗，产出 listings.clean.json + 质量报告
node scripts/slots.ts --md   # 导出「系统到底会抽取哪些字段」的表格
```

**`GOOGLE_MAPS_API_KEY` 缺失时不会崩**：通勤约束整条降级为「这一轮没按通勤筛」，界面上标出来，其余功能完全正常（见 `src/lib/transit.ts:254` 的 `UnavailableTransitProvider`）。这是刻意的——外部依赖不可用时，产品应当少一个功能，而不是变成一堆报错。

**技术栈**：Next.js 16（App Router）· React 19 · TypeScript 6 · Node ≥22.6 直接运行 `.ts`（无编译步骤）· `@anthropic-ai/sdk` + Claude Sonnet 5 · 部署在 Vercel。

无数据库、无状态存储：对话状态由前端持有，每次请求带上来。500 条清洗后的房源常驻进程内存，检索是毫秒级。

## 2. 产品定位与核心原则

### 为谁解决什么问题

租房网站的搜索框有一个共同的失败模式：**你填完所有条件，它给你 0 个结果，然后什么都不说**。你不知道是预算差 50 块还是地段根本不可能，只能回去一个个试。

而在新加坡租房，用户开口时说的往往不是可执行的条件：

> "I work near Raffles Place, somewhere I can get to the CBD in under 40 min by MRT"

这句话里没有一个字是「区域」或「预算」。它是一个**通勤诉求**，需要被翻译成可计算的约束。

所以这个产品的定位不是「会聊天的搜索框」，而是：

> **把模糊的生活诉求翻译成可执行的约束，并在无解时把差距量化出来。**

三件具体的事：

| 用户的状态 | 产品做什么 |
|---|---|
| 说不清要什么 | 主动追问——但只问**能切开候选集**的那个问题 |
| 条件能满足 | 检索 + 加权排序 + 逐条给出推荐理由和需要注意的点 |
| 条件互相打架 | 说清楚差多少，并给出「松哪一条、能多几套」的带数字的选项 |

### 核心原则：代码做决定，模型只负责讲人话

整个系统的骨架是这一条。它决定了架构长什么样：

```
用户说话 → LLM 抽取 → 代码校验 → 代码归并状态 → 代码检索 → 代码决定分支 → LLM 讲成人话
           ↑ 理解                                    ↑ 产品决策
```

**LLM 只出现在两端**：把自然语言变成结构化 patch（理解），把确定的结果讲成话（表达）。中间所有的判断——该不该追问、该不该给放宽建议、哪套排第一、放宽后有几套——全在代码里，是确定的、可测的、不会因为模型今天状态不同而变化的。

为什么这么设计？因为这类系统最贵的错误不是「答得不好」，而是**看起来很合理但其实是编的**。三个具体后果：

1. **不会编造硬约束**。模型可以提议 `areas: ["Kent Ridge"]`，但校验层会因为它不在闭集里而丢弃（`src/lib/extract.ts`）。
2. **不会虚报数字**。「松到 $990 能多 5 套」是真的数出来的，不是模型估的。
3. **行为可测**。213 个测试锁住的是分支逻辑和检索语义，不需要跑模型。

后面每一节的设计取舍，基本都能回到这一条。

### 架构与数据流

一次对话请求走过的路径（`src/lib/agent.ts` 是编排层）：

```
浏览器
  │  POST /api/chat  { conversation, userText }        ← 状态由前端持有，接口无状态
  ▼
① 抽取     claude.ts → extractRequirements()           ← LLM 调用 #1（tool use）
                ↓ 原始 patch
② 校验     extract.ts → validatePatch()                ← 闭集 / 类型 / 词面证据
                ↓ 可信 patch
③ 归并     state.ts → applyPatch()                     ← 纯函数，confidence / pin 决定谁赢
                ↓ RequirementState
④ 检索     search.ts → searchListings()                ← 纯同步：硬过滤 + 加权评分
                ↓ 候选集
⑤ 通勤     commute.ts → applyCommuteFilter()           ← 唯一的外部查询（Google）
                ↓ 结果 + 门到门分钟数
⑥ 分支     agent.ts                                    ← 产品决策：clarify / results /
                ↓ situation + 素材                        sparse / empty / relax / conflict
⑦ 回复     claude.ts → generateReply()                 ← LLM 调用 #2
                ↓
浏览器      { reply, hits, commute, relaxations, conversation, changes }
```

每轮固定两次模型调用。分层有一条硬规则：

> **`search.ts` 必须保持纯同步。**

通勤要发网络请求，塞进谓词里会让 `searchListings` 变成 async，所有调用点和测试都得跟着改，而且引擎从此不可能在没有网络的环境下跑。所以外部查询单独占一层（`commute.ts`），并且 `TransitProvider` 是**注入**的——测试塞一个不联网的桩，213 个测试因此一个网络请求都不发。

## 3. 数据清洗

`data/listings.json` 是 502 条合成房源，其中混了脏数据：格式不一的租金、重复行、缺字段、区域名拼写不统一、离谱的价格。

清洗产出三个文件：`listings.clean.json`（业务数据）、`quality-issues.jsonl`（逐条问题）、`quality-report.json` / `.html`（汇总）。

```
502 行  →  去重后 500 行  →  可推荐 494 行（排除 6 条）
共记录 56 条 issue
```

### 3.1 创新点：三级严重度，而不是「删掉 or 留下」

大多数清洗脚本只有两种结局：修好，或者扔掉。但租房数据里的问题**危害程度差别极大**——租金写成 `"S$1200"` 和租金写成 `0` 完全不是一回事。

所以定义了三级（`src/lib/types.ts:75-79`）：

| 严重度 | 产品行为 | 典型规则 | 条数 |
|---|---|---|---:|
| **block** | 移出推荐池，用户永远看不到 | `rent_outlier_low` 3 · `duplicate_exact` 2 · `rent_zero` 2 · `rent_outlier_high` 1 | 8 |
| **warn** | 照常推荐，但 agent 回答时**必须披露** | `size_missing` · `mrt_missing` · `district_missing` · `bedrooms_contradiction` 各 6 | 24 |
| **info** | 自动规范化，不影响任何人，仅留审计痕迹 | `rent_format_string` · `deposit_format_string` · `available_from_text` · `area_normalized` 各 6 | 24 |

**优势**：warn 这一档是关键。缺面积的房源不该被删掉——它可能正是用户要的那套；但也不能假装数据完整。它照常参与推荐，卡片上挂一个 `⚠ Size not listed`，agent 回答时也会提。**不确定性被显式暴露，而不是被抹平**。

还有一个和 severity **正交**的维度 `escalation`（`src/lib/types.ts:82-86`）：severity 说的是「产品怎么表现」，escalation 说的是「要不要人来管、管的人是谁」。两者不能合并——缺面积在产品上只需 warn，但运维上确实该有人去找房东补；而租金写成 `"S$1200"` 是 info，也确实不需要任何人管。

### 3.2 创新点：租金离群用「同类中位数比值」，不用全局分位数

**朴素做法**：算全部房源租金的 P1/P99，砍掉两头。

**为什么不行**：库里 whole_unit / Landed 这一组的中位数是 $15,600（n=18），最高 $24,350——全都合法。全局砍尾会把这批真实房源当成异常删掉，同时放过 room 类目里 $185 的掉零错误（$185 在全局分布里一点也不极端）。

**我们的做法**（`scripts/clean.ts:353-385`）：按 `listingType × propertyType` 分组，各组内算中位数，用**比值**判定：

```
ratio = 该房源租金 / 同类中位数
ratio < 0.25  或  ratio > 4   →  block
```

中位数对离群值本身是稳健的（不像均值会被 $24,350 拉高），比值又让不同量级的类目可以用同一个阈值。实测抓到 3 条过低、1 条过高，全部是真正的错误：

| 房源 | 原值 | 同类中位数 | 比值 | 建议修复 |
|---|---:|---:|---:|---|
| SG0173 | 185 | 1,950 | 0.09 | 1,850（掉零，置信 0.95）|
| SG0395 | 245 | 1,950 | 0.13 | 2,450（掉零，置信 0.74）|
| SG0400 | 270 | 1,950 | 0.14 | 2,700（掉零，置信 0.62）|
| SG0387 | 62,500 | 5,775 | 10.82 | 6,250（多零，置信 0.92）|

### 3.3 创新点：修复建议不写回业务字段

SG0173 的租金写成 `185`，同类（room / Condominium, n=114）中位数是 $1,950，`ratio = 0.09`——一眼就是掉了一个零。系统会算出建议（`src/lib/normalize.ts:144-162`）：

```json
{ "proposed": 1850, "rule": "dropped_digit", "confidence": 0.95 }
```

判定方式是把 `value×10` 和 `value÷10` 试一遍，看哪个落回同类中位数的合理带（0.4–2.5 倍）。

但这个建议**只进质量报告，绝不写回 `monthlyRentSgd`**。理由：租金错误在租房场景里伤害最大——用户按 $185 约看房、到场发现是 $1,850，产品的信任就没了。而且 agent 拿一个推断值去讲推荐理由，本身就违背 grounding。**系统提建议，改不改由人决定。**

### 3.4 其余几条设计

**解析器是白名单模式**（`src/lib/normalize.ts:4-7`）。租金支持 `1200` / `"S$1200"` / `"4400/mo"` / `"$5550 negotiable"` 四种写法，不匹配任何一种就返回 `null` 并上报 issue。**刻意不写「万能」正则**：一个宽松的 `\d+` 提取器遇到没预料的格式会静默返回一个错误数字，这比解析失败危险得多。顺带从 `"negotiable"` 捞出了业务信号——用户问"能不能砍价"时有据可依。

**区域名归一用多数票，不用 title-case**（`src/lib/normalize.ts:89-102`）。`trim → 折叠连续空格 → 小写` 只作为**分组键**，最终写法取组内出现频次最高的那个原始拼写。因为语料里 `one-north` 的正确写法就是全小写，机械 title-case 会把它改成 `One-North`——一个数据里不存在的名字。

**district 回填只用数据内部的共现关系**（`scripts/clean.ts:324-337`）。某条房源缺 district 时，看同一个 area 的其他房源多数填的是哪个邮区。**不引入任何外部地理知识**——数据是合成的，真实世界的邮区划分未必适用，回填出来的值还会被标记 `districtInferred: true`。

## 4. 需求抽取与对话状态

### 4.1 状态是一份显式档案，不是消息历史

多轮对话最常见的做法是把历史消息全塞给模型，让它自己记住用户要什么。这在这个场景里不可接受：用户要能**看见系统理解成了什么**，还要能**改**。

所以状态是结构化的（`src/lib/state.ts`）：

```ts
type RequirementState = {
  values: SearchQuery,                     // 槽位 → 值
  meta: Record<SlotKey, {
    turnSet: number,                       // 第几轮写入的
    confidence: number,                    // stated=1.0, inferred=0.5
    source: "stated" | "inferred",
    pinned: boolean,                       // 用户说了"必须"
  }>,
}
```

模型每轮只产出一个 **patch**（只含变化的槽位），归并由纯函数完成。带来三个好处：

- **改主意不误伤**。没提到的槽位保持原样——用户第 5 轮说"预算提到 2500"，不会把第 2 轮说的"要能做饭"弄丢。
- **推断值不覆盖原话**。`confidence` 决定优先级：用户明说的 1.0，从上下文推断的 0.5。系统猜"学生大概想租单间"不会盖掉用户后面明确说的"要整租"。
- **底线可标记**。`pinned` 的槽位，放宽推演永远不碰——用户说了"必须能带猫"，系统不会建议他放弃猫。

`values` 的类型直接复用检索层的 `SearchQuery`：**状态里能存的，就是检索能用的**，字段改名会在编译期报错，不存在「记下来了但筛不了」的字段。

### 4.2 系统到底会抽取哪些字段

### 4.3 创新点：模型可以提议，代码负责核对

抽取走 **tool use**（不是 structured outputs）。原因很实际：structured outputs 要把 schema 编译成语法约束，22 个可选槽位会直接撞上 `Schema is too complex` 报错；非 strict 的工具 schema 不走这条编译路径，拿到的同样是结构化 JSON。

但**schema 只保证形状，保证不了内容**。所以每一个模型输出都要过 `validatePatch`（`src/lib/extract.ts`）：

| 检验 | 拦住什么 |
|---|---|
| 闭集校验 | `areas: ["Kent Ridge"]`——听起来很合理，但数据里没有这个区域 |
| 类型校验 | `budgetMax: "2500"`、负数、`requireCooking: "true"` |
| 日期格式 | `moveInBy: "九月"` |
| 词面证据 | 见下 |
| set/clear 冲突 | 同一槽位既 set 又 clear 时，set 赢（视为替换，而不是删除） |

**词面证据（lexical evidence）是这一层最有意思的一条**。起因是一次真实的编造：用户说

> "Location matters a lot — the children will study around Bukit Timah, so somewhere close would be great."

一个字都没提交通工具和时长，系统却抽出了 `by DRIVE, under 20 min`——两个都是硬过滤条件。用户完全看不出这个 20 分钟是哪来的，也不知道自己被它挡掉了多少房源。

更麻烦的是这个编造是**间歇性的**，同一句话复现两次都正常。所以**不能靠在 prompt 里加一句"不要编造"**——必须有代码层面的客观检验：

```ts
// src/lib/extract.ts
const MODE_EVIDENCE = {
  drive: /\b(driv\w*|car|vehicle|motorbike|scooter)\b/i,
  mrt:   /\b(mrt|train|subway|metro|rail|\w+ line)\b/i,
  ...
};
const DURATION_EVIDENCE = /\b(min|mins|minute|hour|hr)\b|\d\s*(mins?|hours?|hrs?|m|h)\b|half an hour/i;
```

模型给的 `mode` / `maxMinutes`，必须能在**用户这一轮的原话里**找到对应词，否则丢弃（已经存在且没变的值豁免，否则重提目的地会把上一轮说好的时长弄丢）。

这是整个项目的方法论缩影：**prompt 是引导，校验才是强制力。**

### 4.4 相对调整：模型只给方向，代码算数值

用户说"再便宜点"时，模型**不允许自己算数字**，只能返回方向：

```json
{ "adjust": [{ "slot": "budgetMax", "direction": "down" }] }
```

具体幅度由固定档位算（`NOTCH_STEP`，见 §7）。三个好处：模型不用猜数（也就不存在"这个数是不是推断的"这种争议）、调整幅度和放宽建议全系统一致、结果完全确定因此可测。

还有一条防线：**"That one's a bit pricey" 不触发 adjust**。那是对某一套房的评价，不是对整体预算的修改——静默把预算砍 10% 会给用户看一个他从没说过的数字。

### 4.5 追问：只问能切开候选集的那个问题

约束不足 2 条时才追问，而且**只问一句**。问哪一句由代码算（`src/lib/state.ts:315-408`）：

```
问题价值 = 领域先验权重 × 在当前候选集上的区分度
```

- **先验**：预算 1.0 > 整租/单间 0.95 > 区域 0.9 > … > 水电 0.2。这是租房这个领域里"通常多重要"。
- **区分度**：数值字段用变异系数，类别字段用归一化熵。**如果剩下的房源在某个字段上取值几乎一致，问它的信息量就是 0**——候选全都允许做饭时，"需要能做饭吗"是一句废话。

另外有两条确定性兜底：连续追问最多 2 轮，之后无论如何给结果；用户说"别问了直接给我看"时立刻停止追问。**用户宁可看到不够精准的房源，也不想被盘问第四遍。**

## 5. 通勤：从算不出来到真实路线

这一节单独拿出来讲，因为它是整个项目里最曲折、也最能说明取舍的一块。

### 5.1 困境

房源数据里的 `nearestMrt` 只有三个字段：

```json
{ "station": "Clementi", "line": "EWL", "walkMinutes": 7 }
```

**没有任何站间行程时间**。所以「40 分钟内到 Raffles Place」这个要求，用数据本身**根本算不出来**。

而它偏偏是最高频的诉求——10 个示例 session 里有 7 个提到了"我在哪上班/上学"或"要多久能到"。

### 5.2 第一版是错的

系统一开始没有「目的地」这个概念，模型只好把这句话硬塞进已有的槽位：

```
"under 40 min by MRT to Raffles Place"
  → maxWalkMinutes: 40  +  stations: ["Raffles Place"]
```

两个都错得很典型：
- `maxWalkMinutes: 40` 在 494 套上**全部通过**（等于空转，但看起来像个真约束）
- `stations: ["Raffles Place"]` 要求房子就在那一站旁边——把一个几乎不排除任何东西的要求，变成了整个查询里最紧的一条

**结果：21 套 → 0 套。** 根因不是模型笨，是**槽位表里没有"目的地"这个概念，它无处可放**。

### 5.3 接入 Google Distance Matrix

加了 `commute` 槽位之后，行程时间必须来自外部。选 Distance Matrix 而不是逐条查路线：**一次请求能带 25 个起点**，85 个站分 4 次就查完，并发下约 1 秒。

这个性能事实改变了架构：不需要"先缩小候选再算通勤"那套顺序依赖，可以直接全量算，`commute` 于是能当成普通硬约束用。

```
门到门总时长 = listing.nearestMrt.walkMinutes   （房源数据自己的字段）
             + transit(该站 → 目的地)            （Google）
```

房源在地图上的位置只能用别的字段近似——数据里没有门牌号和坐标，所以有一条降级链：

```
① nearestMrt.station   最准的一档，还附带"走到站几分钟"
② area                 500 套里有 6 套没有 nearestMrt（按区域算时不叠加步行段）
③ 都没有               才真的算不出来
```

第 ② 条是被一个真实 bug 逼出来的，见 §10.6。

几个必须做对的细节：

**① 出发时刻必须固定，而且必须是新加坡时区**（`src/lib/transit.ts:45-52`）。公交行程时间随时刻变化（末班车、班次密度），不固定参考时刻，同一套房深夜查和早高峰查结果不同，推荐就不可复现。选下一个工作日 **SGT 09:00**，因为用户问的就是上班通勤。踩过的坑见 §10.1。

**② 出行方式必须进缓存键**。同一个目的地开车 15 分钟、地铁 40 分钟，键里不带 mode 的话两者会互相覆盖，用户问开车却拿到地铁的数。

**③ 驾车用 `duration_in_traffic`**。新加坡高峰期和空载能差十几分钟，那个才是用户真正会花的时间。

**④ 步行到站那一段只对公共交通成立**。开车的人不会先走 5 分钟到地铁站再上车。

**⑤ 目的地不走闭集**。用户要去的地方可以是 NUS、樟宜机场、某家医院——这些都不在房源词表里。拿闭集卡目的地会把作业原文给的示例问题 "how far is it from NUS?" 直接丢掉。**能不能解析交给 Google 判断，比拿一份房源词表去猜世界上有哪些地方要准得多。** 防编造的活改由词面证据承担（§4.3）。

### 5.4 三条降级路径，全部遵循「缺失 ≠ 不满足」

外部依赖一定会出问题，关键是出问题时的行为：

| 情况 | 行为 |
|---|---|
| 房源没有最近地铁站 | 用它的 `area` 当起点（精度差一档，但算得出来）；连 area 都没有才计入 `unverified` 并**放行** |
| 某个站查不到路线 | 只有那几套算 `unverified` 并放行，其余照常筛 |
| 目的地解析失败 / 服务不可用 | **整条约束降级，一套都不筛**，并在界面和回复里明说 |

第三条尤其重要：**这比"筛出 0 套"好得多**。筛出 0 套时用户会以为是自己条件太苛刻，而真相是系统算不出来。

### 5.5 默认 40 分钟

用户说"我在 Jurong East 上班"却没给分钟数时，系统按 **40 分钟**卡（`src/lib/commute.ts:44`）。

这**不是**模型编的数字（那种编造见 §4.3），而是一条固定的产品默认值：对每个用户都一样、写死在代码里、**并且在侧栏和回复里都明说是默认值**：

```
Commute    to Jurong East, by MRT, under 40 min (default)
```

> "I've kept these within 40 minutes of Jurong East since you didn't give a specific time limit — tell me if you'd trade a longer commute for more options."

为什么要筛而不是只排序：说了在哪上班本来就是在表达通勤诉求。只排序会让通勤一小时的房源照样出现在结果里，用户还得自己一张张核对。

## 6. 检索、评分与推荐

### 6.1 硬过滤：缺失 ≠ 不满足

23 个槽位里 22 个是内存谓词（纯函数、可测），commute 那一条在外部查询层。

贯穿所有谓词的一条规则：**字段缺失时不参与该项筛选，而不是判为不满足**（`src/lib/search.ts:251`、`278`）。

用户要 ≥800 sqft，某套房没填面积——它可能正好合适，房东只是漏填了。做法是**放行 + 在卡片上披露**（`⚠ Size not listed`），让用户自己判断。房东漏填一个字段，不该让用户错过一套合适的房子。

检索同时产出 `excludedBy`（每条约束单独砍掉了多少套）和 `pool`（参与筛选的基数），是后面放宽推演和排错的依据。

### 6.2 加权评分

硬过滤决定「能不能出现」，评分决定「排第几」（`src/lib/search.ts:128-137`）：

| 维度 | 权重 | 算的是什么 |
|---|---:|---|
| `budgetFit` | 2 | 相对预算上限的余量 |
| `commute` | 2 | 有目的地时用**真实门到门分钟数**；没有时退化为走到地铁站的分钟数 |
| `size` | 1.5 | 相对用户下限的余量 |
| `furnishing` | 1 | 是否命中偏好 |
| `amenities` | 1 | 命中比例 |
| `freshness` | 0.5 | 房源发布距今天数（7 天满分，90 天归零） |
| `availability` | 0.5 | 可入住日期和用户期望的间隔 |

预算和通勤持平，都是 2。**预算不该主导排序**——它是"别超"，不是"越便宜越好"；一套便宜 $300 但通勤多 40 分钟的房子，不该因为便宜就排第一。

衰减用统一的 `decay(value, best, worst)`：好于 best 得 1 分，差于 worst 得 0 分，中间线性。

**创新点：`raw: null` 的维度不进分母**（`src/lib/search.ts:502-513`）。

```
总分 = Σ(适用维度的加权分) / Σ(适用维度的权重)
```

某套房没有面积数据，`size` 维度就整个不参与，而不是当成 0 分。否则**「没数据」会被算成「得分低」**，数据完整度高的房东会系统性地占便宜——这是一种和房源质量无关的偏见。

评分还带 `breakdown`（每个维度的原始分、权重、**证据字符串**），推荐理由因此永远引用具体字段值：

```
"38 min door-to-door to Raffles Place"
"7 min walk to Clementi (EWL)"
```

而不是"交通便利"这种模型可以随口说的定性评价。

### 6.3 卡片上的 ✓ 和 ⚠

每套房带两组标签，都是代码生成的：

- `matched`——命中的硬约束：`✓ Under $2,000/mo`、`✓ Cooking allowed`
- `caveats`——**必须披露**的事项：`⚠ Size not listed`、`⚠ Owner prefers female tenants`

原则同上：**不确定性要显式暴露，而不是抹平**。

## 7. 放宽推演：找不到房的时候

这是「0 个结果 + 什么都不说」那个失败模式的正面回答。

### 7.1 固定档位

放宽幅度不由模型决定，走固定档位（`src/lib/search.ts:639-647`）：

| 约束 | 一档 | 为什么这么定 |
|---|---|---|
| 预算 | +10% | 按比例，跨价位可比 |
| 面积下限 | −10% | 同上 |
| 步行到 MRT | **+5 分钟**（绝对值） | 按比例的话，3 分钟只放宽 18 秒，毫无意义 |
| 最长租期 | **×2** | 6 个月的下一档是 12，不是 6.6 |
| 通勤 | **+15 分钟**（绝对值） | 5 分钟太小，30 分钟等于换个活法 |
| 房型 / 整租单间 / 家具 | 取消该限制 | 这类是集合，没有"松一点" |

**和用户说"再便宜点"共用同一组常量**——否则用户会发现"我说再便宜点"和"系统建议放宽预算"的幅度对不上。

### 7.2 每一条都真的数一遍

推演不是估计：对每个候选方案，拿放宽后的查询**重新跑一遍完整检索**，得到 `delta = 放宽后 − 放宽前`，按增量降序排。

**有通勤约束时必须走异步版本**（`src/lib/commute.ts`）。纯内存版不知道放宽后新进来的房源还得再过一遍通勤，实测偏差不小：

```
预算 $900 + 通勤 ≤40 分钟，当前 9 套
纯内存版：  "松到 $990 能多出 5 套"
算上通勤：   实际只多 2 套
```

这个数字是用户做决定的依据（"多 5 套值得我多花 $90 吗"），**虚报就是误导**。

### 7.3 保留 delta = 0 的结果

`rankRelaxations` 返回**全部**推演结果，包括增量为 0 的（`src/lib/search.ts:855-865`）。

因为「所有单档放宽都无济于事」本身是关键信号——它意味着冲突是**结构性的**，不是差一点点。只吐正增量的话，调用方就无法区分「没有可放宽的约束」和「放宽了也没用」，而这两种情况该说的话完全不同。

### 7.4 结构性冲突：给事实，不给过程

单档放宽全都无效时，走 `conflict` 分支，用 `src/lib/insight.ts` 算「**只保留某一条约束、放开其余全部**，库里实际是什么情况」：

> "在你想要的那一带，最便宜的是 $2,800，离 $1,500 还有一段距离。"

**朴素做法是把 `excludedBy` 给模型**（"494 套里被排除了 475 套"）——那是检索过程，用户不关心。他想知道的是"那我到底要多少钱才够"。

更糟的是，模型拿到那种数字会自己补一句解释："City Hall 是市中心核心地段，房租普遍偏高。"这句话来自它的真实世界知识，**不是我们的数据**——而我们的数据是合成的，库里那一带到底贵不贵得查了才知道。**听起来最自然的那句话恰恰是幻觉。**

### 7.5 节奏：先邀请，再给清单

命中 0 或 ≤5 套时，**第一次只共情 + 邀请，不给清单**：

> "没有同时满足这些条件的房源。要不要放宽点什么？我看看能多出多少。"

一上来就甩一张放宽清单，等于替用户做了他还没做的决定。**但他直接开口问**（"哪条最难满足？""我该让步什么？"）是另一回事——那是在要这个分析，还按套路走就是答非所问，而且答案本来就是现成的：增量最大的那条就是最卡的那条。

### 7.6 创新点：用户点头之后，改动由代码应用

这是最后修的一个 bug，也是最能说明「代码做决定」这条原则的例子。

```
agent  "放宽到 35 分钟能多出 5 套，要我这么搜吗？"
用户   "sure thing"
系统   ……侧栏还是 under 20 min，结果还是 0 套
agent  "这就给你调出来"        ← 说了要做，什么都没做
```

根因：放宽方案只带了**说辞**，没带**改动**。所以"应用它"唯一的指望，是模型照着自己上一句话把 `35` 再说一遍——而通勤时长还要过词面证据校验，`sure thing` 里一个时间单位都没有，必然被丢掉。

改法：**每条方案生成时就带上它对状态的确切改动**（`patch`），摆给用户的方案存进 conversation，模型只负责认出「他答应的是哪一条」（key 走闭集），**数字全程不经模型的手**。

测试锁死的关键不变式：

```
patch 打回原查询  ===  这条方案自己评估过的那个查询
```

用户看到的"多 5 套"是按前者数的，点头后应用的是后者——两者对不上，就是又一次"我答应的和我拿到的不是一回事"。

放宽应用因此有两个入口，共用同一份 patch：
- 接受上一轮摆出的方案（key 在 `offeredRelaxations` 里核对）
- 自己点名要松哪一条（"relax the commute window"，key 在本轮候选里核对）

## 8. 界面设计

单页：左侧对话流，右侧「我理解到的条件」。

### 8.1 房源卡片与醒目编号

每套房是一张卡片：标题、租金、区域/邮区/面积/最近地铁站/最短租期/可入住日期，下面一行标签。

**编号做成了醒目的徽章**，这是刻意的：

```
[SG0469 #1]  Common Room in Bungalow, Buona Vista              $1,750 /mo
Buona Vista · D05 · 188 sqft · 5 min walk to one-north (CCL) · 3-month min lease · From 2026-08-05
🚇 14 min door-to-door   ✓ Under $2,000/mo   ✓ Cooking allowed   ✓ No agent fee
```

因为 **agent 在聊天里用 `SG####` 指代房源**（"如果通勤最重要，看 SG0469"）。编号是用户在对话和卡片之间对照的唯一线索，它必须一眼能找到。排名 `#1` 做成上标附在旁边——够用，又不抢戏。

通勤时间用**单独的样式**（🚇 芯片）标出来，因为它和其他字段来源不同：那是真实公交数据，不是房源自带的字段。

### 8.2 侧栏：把状态摊开给用户看

侧栏逐条列出当前生效的条件，每条可以：

- 看到来源标记（`must` = 用户说了"必须"，放宽推演永远不碰）
- 看到系统默认值（`under 40 min (default)`）
- **点 ✕ 删除**

✕ 不是偷偷改状态，而是**替用户说一句话**——它会往对话里发送 "Drop the max budget requirement"，走同一条抽取管线。这样对话记录里留得下痕迹，**用户看到的和系统做的始终一致**。

通勤那一条如果这一轮没能真的参与筛选（外部服务不可用），会挂一个橙色的 `not filtered` 标记。用户必须能看出「记下来了」和「筛过了」的区别。

### 8.3 出错时可以重试

模型 API 过载（529）时，那一轮显示错误卡片 + **Retry 按钮**。重试时失败的那一轮**原地复活**，而不是在末尾追加一条——用户没有重新说话，对话记录里就不该出现第二条同样的话。

服务端也有针对性重试：529 是容量信号，不是请求有问题，唯一有效的应对是等久一点（3s → 8s）。SDK 自带的秒级退避对付持续几分钟的容量过载没有用。

## 9. 难 case 的处理

### 9.1 矛盾需求

见 §7.4。核心是**不解释、只给事实**：说清楚只保留某一条时库里的实际情况，让用户自己判断该动哪一条。

### 9.2 敏感请求（国籍）

数据里有 `tenantPreferences.nationality`，值形如 `"Chinese only"`。处理分两侧：

**检索侧：没有、也不会有 nationality 过滤器**（`src/lib/search.ts:364`）。而且**模型在 schema 层面就无法产出国籍偏好**——`ExtractedPatch` 里根本没有这个字段。这不是"拒绝配合"，是**系统做不到**。防线往前推了一层：不是"不用"，是"表达不出来"。

**展示侧：exclusive 的限制必须提前告知**（`src/lib/search.ts:537-551`）：

> ⚠ Owner states a nationality preference ("Chinese only") — this may affect your application

这不是在执行歧视，是**保护用户不白跑一趟**。房东的限制客观存在，瞒着用户没有任何好处。

性别的处理不同：`tenantGender` 是可筛的，因为合租房的性别限制在新加坡是常规且合法的房源属性；但它不计入"够不够检索"的约束数——它是保护性字段，不是用户的择房偏好。

### 9.3 无完全匹配

见 §7 整节。三段式：共情 → 邀请 → 给带数字的方案。

### 9.4 脏数据

见 §3.1 的 warn 档 + §6.3 的 caveats。**照常推荐，但必须披露。**

### 9.5 追问已展示的房源

用户问"top pick 详细说说""能议价吗"时，状态没变 ⇒ 检索结果和上一轮**逐条相同**，整批再贴一遍纯属刷屏。所以这时不重贴卡片，但**回复里点到名的那几套仍然要贴**（用正则从回复里抓 `SG####`），否则用户得往上翻才能看到你在说哪套。

这个判断必须在分支之前算——否则"上一轮结果很少"会被当成"用户愿意谈放宽"，于是他问一句 top pick，回复末尾却挂着"要不要我说说放宽哪条能多出选择？"

## 10. 开发过程：七个真实的坑

这一节是这个项目最有信息量的部分。每个都是**测试没覆盖到、只能靠真跑才暴露**的问题。

### 10.1 时区：把 45 分钟算成 5 小时 10 分

**现象**：Pasir Ris → Raffles Place 查出 **5 小时 10 分钟**（真实约 45 分钟）。

**根因**：`d.setHours(9, 0, 0, 0)` 用的是**服务器的本地时区**。开发机在 PDT，"明天 9 点"算出来是新加坡**周日凌晨 0 点**——Google 只能等首班车。部署到 Vercel（UTC）则会变成新加坡下午 5 点晚高峰。**两种都是错的，而且错得很隐蔽：返回的是合法数字，只是答的不是同一个问题。**

**改法**：新加坡是 UTC+8 且不实行夏令时，所以 09:00 SGT 恒等于 01:00 UTC 同一天，全程用 UTC 方法即可，不需要时区库。加了 3 个测试：覆盖一整年的日期、永远落在工作日、永远是将来的时刻。

### 10.2 `JSON.stringify(new Map())` 是 `"{}"`

**现象**：通勤筛选正常、模型也拿到了分钟数，但**前端卡片上的时间死活不显示**。

**根因**：`commute.minutes` 是 `Map`，过 JSON 之后变成 `{}`。不报错，数据静悄悄地没了。

**改法**：加了 `CommuteSummary` 类型（`Record<string, number>`）和 `toSummary()`。**凡是要过 JSON 的地方都得摊平**——现在有 2 个测试专门锁这个。

### 10.3 模型三次凭空捏造硬约束

同一个模式，在三个不同字段上抓到三次：

| # | 用户说的 | 系统抽出的 | 后果 |
|---|---|---|---|
| 1 | "under 40 min by MRT to Raffles Place" | `maxWalkMinutes: 40` + `stations: [Raffles Place]` | 21 套 → 0 套 |
| 2 | "the children will study around Bukit Timah, so somewhere close would be great" | `mode: DRIVE`, `maxMinutes: 20` | 凭空多两条硬过滤 |
| 3 | 同上 | `areas: [Bukit Timah, Upper Bukit Timah]` | 通勤 38 分钟的合适房源被直接扔掉，结果 0 套 |

三次的共同点：**系统替用户加了一条他没说过的限制，然后告诉他"没有符合的"**。用户看不出是被什么挡住的，只会以为自己要求太高。

第 2 个尤其麻烦：**同一句话我复现两次都正常**，是间歇性的。这直接证明了 prompt 改不动它——**必须有代码层面的客观检验**：

1. 加 `commute` 槽位，让"目的地"有地方放（第 1 个）
2. 词面证据校验 mode / maxMinutes（第 2 个）
3. 软偏好进**排序**而不是**过滤**（第 3 个）——"住附近就好"应该让近的排前面，而不是把远的扔掉

### 10.4 目的地闭集把 NUS 吃掉了

**现象**：用户说 "i'm a nus student, find me a room where i can go to school within 30mins"，agent 回答"我查不了行程时间"。

**根因**：`commute.destination` 走的是房源数据的闭集（区域∪站名∪邮区）。**NUS 不在里面** → 整条通勤约束被静默丢弃 → 侧栏连痕迹都没有。作业原文给的示例问题 "how far is it from NUS?" 同样会被这条规则吃掉。

**改法**：目的地改为开放字段，防编造的活换给词面证据。这一条和 §10.3 是**同一道闸门的两侧**：闭集拦住了编造，但也拦住了合法的世界；词面证据只拦编造。

### 10.5 "30mins" 里没有词边界

**现象**：修完上一条之后线上验证，用户明说的 30 分钟变成了系统默认的 40 分钟。

**根因**：时长证据的正则是 `\bmin`，而 **`30mins` 里 min 前面没有词边界**。用户自己说的条件被判为"没依据"丢掉，反倒套上了系统默认值。

**用户明说的条件被系统默认值顶掉，比不做默认值还糟。** 加了第二条分支处理"数字和单位连着写"，同时保留 `\b`——因为 `min` 是 `administrator`、`terminal` 的子串，去掉边界之后随便一句话都能给编造的时长背书。

### 10.6 「算不出来」被当成了「合格」

**现象**：用户要「步行 20 分钟到 NUS」，唯一一套结果是 SG0154（Bukit Panjang），还排第 1。而 Bukit Panjang 走到 NUS 要 **148 分钟**。

**根因**：SG0154 没有 `nearestMrt`（500 套里有 6 套这样），当时定位只认这一个字段，于是算不出通勤时间 → 按「缺失 ≠ 不满足」放行 → 又因为别的维度分高排到了第 1。

**这是把一条防误伤的原则用错了地方。** 「缺失 ≠ 不满足」本来是保护用户不错过合适房源，却被当成了**合格**——一套核算不了的房子不仅没被排除，还顶替了真答案的位置。而它 `area` 明明写着 Bukit Panjang。

**改法**：加了 station → area → 无 的降级链（§5.3）。修完之后同一个查询返回 0 套，并给出"最接近的几套在 21–26 分钟，放宽到 25 分钟？"——**0 套比给你一套走三个小时的房诚实得多**。

### 10.7 用户点了头，系统当没听见

见 §7.6。这个 bug 有两个入口，修了第一个之后又撞上了第二个：

- 接受**上一轮摆出的方案**（"sure thing"）——第一次修
- **自己点名**要松哪一条（"yes, relax the commute window"）——当时 `offeredRelaxations` 还是空的，匹配不上，于是走回"介绍一遍方案再问一次"的老路，**要求用户点两次头**

### 小结：这些坑的共同形状

七个里有六个是**「系统做了一件事，但用户看到的是另一件事」**：

- 算出来的不是用户问的那个时间（10.1）
- 拿到了数据但没显示（10.2）
- 加了用户没说过的约束（10.3）
- 丢了用户说过的约束（10.4、10.5）
- 「不知道」被当成了「符合」（10.6）
- 用户的决定没有被执行（10.7）

**测试全绿也拦不住这一类**——它们的共同点是「代码逻辑正确，但语义和用户的期待错位」。唯一有效的手段是真的跑一遍，用真实的话去问。所以有了 `scripts/replay.ts`：拿 `data/conversations/` 里的 session 逐轮回放，产出可读的 markdown，用来肉眼过。

## 11. 已知不足与改进方向

**诚实列出来的当前问题**：

1. **数据里表达不了的条件，会被静默丢弃，而回复可能仍当它生效**。实测：用户要 "with refridgerator"——`amenities` 词表里 15 个值全是小区设施（Gym、Swimming Pool、Covered Parking…），**根本没有"冰箱"这个概念**，所以闭集匹配失败，侧栏也没有这一条。但模型看到用户原话，回复里照样说了 "with a fridge"。

   这是**说了一个没在筛的条件**，和 §10.3 是同一个性质，只是方向相反：那边是凭空多筛，这边是假装筛了。当前有两层设计部分覆盖它——`NOT_IN_DATASET`（列出数据集根本没有的信息，如门牌号、房东联系方式）和 `dropped`（被校验层丢弃的抽取结果）——但 `dropped` 目前只进日志，没有喂给回复模型。修法很直接：把它一起给过去，让模型有义务说一句"冰箱这条我没能作为筛选条件用上"。

2. **6 套没有最近地铁站的房源用区域中心近似**。精度差一档，证据字符串里标了 `about ... (from Bukit Panjang, no station listed)`，但用户不一定注意到。

3. **Google 调用只有进程内缓存**。Vercel 冷启动就丢，代价是重新查一次。加个 KV 层可以显著省钱，但要处理失效。

4. **`scripts/slots.ts` 的自动探测标不出 commute 的硬过滤**，因为它在检索层之外。表格里手工标了注记。

5. **成本没有做优化**。抽取和回复各一次模型调用，抽取已经关掉 thinking + effort 拉到最低、系统提示走 prompt caching，但没有做批处理或小模型分流。

**有更多时间会做的**：

- **把示例 session 变成回归测试**。目前 `replay.ts` 产出的是给人看的 markdown，靠肉眼过。可以对**确定性的那一半**（抽取出的槽位、走的分支、命中数）写断言——这些不依赖模型措辞，完全可以自动化。
- **通勤反查**。现在是"给定目的地筛房源"，反过来"这个预算下通勤最短的区域是哪几个"同样有用，数据都是现成的。
- **多目的地**。"我在 Raffles Place 上班，伴侣在 one-north" 是常见诉求，`CommuteNeed` 现在只支持一个目的地。
- **把 `escalation` 队列做成界面**。质量报告已经区分了「谁该去管这条 issue」，但目前只是 JSON/HTML，没有人可以在上面操作。
- **议价信号的利用**。清洗时已经从 `"$5550 negotiable"` 捞出了 `negotiable` 标记，但推荐理由里还没用上。

## 12. 边界声明

**房源数据全部是作业提供的合成数据，一条未换、未接入任何真实房源。**

唯一的外部数据源是 **Google Distance Matrix API**，只用来查**站点/区域 → 目的地的行程时间**。它不提供任何房源信息。门到门时间的构成：

```
walkMinutes（来自房源数据，合成）  +  transit 时间（来自 Google，真实）
```

另外，数据里没有门牌号和经纬度，所以**「最近的地铁站」是我们对"房子在哪"唯一的近似**。这对公共交通是准确的（用户本来就要去那个站），对驾车是一个近似。
